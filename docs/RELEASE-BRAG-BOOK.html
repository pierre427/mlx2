The category distinction

Beyond a framework. Beyond a generic server.

MLX supplies native Apple-Silicon arrays, lazy execution, unified memory, streams, compilation and model-building primitives. mlx2 adds the layer MLX deliberately does not try to be: a production inference control plane with transactional model state, route qualification, memory admission, specialized decoding paths and end-to-end receipts.

Apple SiliconUnified CPU/GPU memory, Metal execution and device working-set constraints.
MLXArrays, operators, lazy graphs, compilation, streams and extensible kernels.
Model mathQwen hybrid attention/recurrent layers, MoE, PLE, GDN, QSA and draft heads.
mlx2 runtimeAPCv2, continuous batching, transactions, admission, speculative execution, route policy and observed-use telemetry.
mlx2 productOpenAI/Hermes API, strict outputs, cancellation, qualification identities, health/status and defensible operating boundaries.

The central brag: mlx2 does not merely expose kernels. It composes kernels, cache state, scheduler policy and API semantics into a single revision-bound transaction—and refuses to claim a feature when its mechanism did not engage.

One connected system

Each feature makes the others safer and more useful.

The architecture is deliberately compositional. Model descriptors keep tensor math out of the scheduler. APCv2 gives every optimization one ownership language. Admission reserves the real footprint before execution. Qualification binds the whole arrangement to evidence. Receipts close the loop at request time.

Serving

OpenAI-compatible chat and text completions

Chat/completions and completions share one bounded request lifecycle, with nonstreaming and SSE streaming responses.

Existing clients can move onto Apple Silicon without giving up a familiar API shape.

How it works

POST /v1/chat/completions and /v1/completions are handled in server.py, which validates the body, renders the adapter's chat template and hands one job to the generation worker in serving.py. Nonstreaming callers wait on the job's event queue; streaming callers receive data: chunks written by _sse. Every successful generation response carries an mlx2 route receipt naming the route, sampling and constraint semantics actually used. Since the page was written, the same lifecycle also backs /v1/responses and /v1/messages: responses_to_chat_request and anthropic_request_to_chat translate those dialects into this chat request shape instead of running a second engine. Output caps now accept 1 to 2,097,152 tokens, and an omitted cap resolves through resolve_output_limit to min(65,536, remaining context). The benefit is one admission, cancellation and receipt path for every client dialect. It composes with Continuous batching with truthful widths, APCv2-only prefix reuse and Mechanism counters and route receipts, and every optimized route, such as Persistent segmented self-MTP and Prompt-lookup decoding, sits behind the same endpoint.

Field check

Chat and text completions are table stakes. As of Sept 2026, vLLM's online-serving docs list /v1/completions, /v1/chat/completions, /v1/responses and the Anthropic /v1/messages pair. LM Studio documents Responses, Chat Completions, Completions and Embeddings plus Anthropic endpoints. oMLX's README lists chat, completions, Anthropic Messages, embeddings and rerank, and mlx-lm's SERVER.md documents /v1/chat/completions and /v1/models. llama.cpp's server README documents an OpenAI-compatible Responses endpoint. Several of these projects expose more endpoints and far more model families than mlx2. mlx2's difference is that every dialect enters one bounded lifecycle and returns a route receipt, not breadth.

Streaming

SSE, cancellation and backpressure

Disconnects and slow consumers cancel work; output queues, connections and inflight requests are bounded.

Runaway clients do not silently become runaway GPU work or unbounded memory.

How it works

Each job owns a bounded event queue. _emit in serving.py uses put_nowait; when a consumer stops draining and the queue is full, it sets the job's cancelled event and replaces the queued tail with a 429 "client did not consume output fast enough" error, so generation stops at the next token boundary instead of buffering without limit. In server.py, broken pipes and connection resets are logged as 499. A nonstreaming client that closes its socket while waiting raises ClientGone, which increments the client_disconnects counter and cancels the job. The finally block cancels every sample job of an n>1 cohort and releases the admission lease. Connections, inflight requests and output queues are bounded. While the server is quiescing, model-executing endpoints return their native OpenAI or Anthropic 503 with Retry-After. The same path serves typed Responses and Anthropic streams (_responses_sse, _anthropic_sse). It composes with Deferred memory admission without lane capture and Dead-worker and stall failure semantics: a cancelled lane releases its reservation rather than holding it.

Field check

Disconnect and cancellation handling is a recurring bug class. Rapid-MLX merged #3022 in Sept 2026 to cooperatively cancel buffered guided decoding, and vLLM merged #55602 and #57024 to fix nested cancellation handlers on its rerank and score routes. vLLM also has an open fix, #46162, to forward upstream error messages in its Anthropic streaming converter. mlx2 has not measured how its 429-on-slow-consumer policy compares with the buffering other servers use, so the claim here is limited to its own bounded queues, counters and cohort-wide cancellation.

Agents

Function calls and Qwen tool parsing

OpenAI-shaped tool definitions, auto/none choice, normalized arguments and Qwen3 Coder parsing integrate with agent loops.

Local inference can participate in real tool-using workflows rather than remain a text-only demo.

How it works

Clients send OpenAI-shaped tools. normalize_tool_choice in openai_compat.py accepts auto, none, required or one named function, and the adapter's parser turns model output into calls: runtime/tool_parsers/qwen3_coder.py for Qwen's XML-style calls, plus adapter parsers for North action blocks, Muse and Laguna (tool_parsers/laguna.py). After generation, enforce_tool_contract checks that required and named choices produced the right call, that parallel_tool_calls:false yields at most one, and that strict schemas validate against the bounded JSON-schema subset used for structured output. Violations return 502; malformed client contracts return 400. Strict, required, named and single-call streams are buffered until the check passes, so no client receives headers for a call that later fails. resolve_local_refs inlines local $ref/$defs pointers. In the 2026-09-19 quality campaign these checks failed closed on Muse, North and Xing when models skipped a required call (PASS-5-TRIAGE.md). Decode-time enforcement is the opt-in card Forced tool calls constrained by grammar, and the same contract backs Responses function tools and Anthropic tool_use.

Field check

Several major servers use model-family-specific tool parsers, and the edge cases are still being fixed. vLLM's open #57553 keeps fenced code examples out of Qwen3 tool calls; SGLang's open #40291 and #40295 preserve LFM2 calls across stream chunks and in nonstreaming text; oMLX merged #3693 to preserve and recover Qwen tool calls; and mlx-vlm merged #2208, moving tool calling into a dedicated package. oMLX's README says it supports all mlx-lm function-calling formats plus MCP integration. These projects cover far more model families than mlx2's adapters. mlx2's distinguishing choice is terminal validation that fails a bad call with 502 instead of returning it to the agent.

Reasoning

Hermes and thinking controls

options, think, enable_thinking, template controls and effort labels normalize into explicit route controls; conflicts and unknowns fail.

Different clients get one deterministic control language instead of accidental template behavior.

How it works

options, think, enable_thinking, chat_template_kwargs.enable_thinking and reasoning_effort are normalized in server.py into one set of route controls before the job is built. Conflicting toggles and unknown options keys or template keys return 400 instead of being ignored. options.num_predict and options.num_ctx map onto the output cap and a per-request context ceiling, and duplicate controls that disagree are rejected. reasoning_effort now accepts eight labels, none through ultra; its meaning is adapter-specific and recorded in the receipt. For Qwen a positive label enables thinking, and the guard scales its budget anchor by effort (minimal 0.125x to high 4x, capped at 8,192). /v1/status.thinking_default reports whether a model thinks when a request says nothing; North-Mini-Code does. Reasoning is returned in reasoning_content, separate from content. Responses reasoning.effort and Anthropic thinking map onto the same controls. They feed Thinking budgets and run-on release and Grammar deferral past thinking, and choose the thinking-mode profile in Vendor sampling defaults per model.

Field check

Thinking toggles are unevenly standardized across servers. oMLX merged #3559 in Sept 2026 to preserve and normalize thinking controls, Rapid-MLX merged #3048 to map reasoning_effort onto a template's native levels, and SGLang merged #39227 to force reasoning mode for GLM-5.3 templates. Ollama's open #17566 notes that its think field today only switches reasoning on or off, and proposes effort levels that resolve to token budgets. vLLM documents per-model reasoning parsers such as qwen3, deepseek_r1 and glm45, and merged #44301 for include_reasoning on non-Harmony models. These projects cover more model families; mlx2's distinction is rejecting conflicting or unknown controls rather than passing them to the template.

Sampling

Full per-request sampling controls

Temperature, top-p, top-k, min-p, seed, stop strings, token caps, logit bias and repetition/presence/frequency penalties flow through ordinary and speculative target laws.

Optimized routes preserve the semantics applications expect from the reference route.

Unset sampling fields now take the adapter's declared vendor profile (for example Qwen thinking mode: temperature 1.0, top_p 0.95, top_k 20) rather than a fixed engine value; the old 0.7/0.8/20 fallback applies only to adapters with no declaration. top_p is now computed in float32 on every device.

How it works

Temperature, top-p, top-k, min-p, seed, stop strings, logit bias and repetition, presence and frequency penalties are resolved per request by resolve_sampling in sampling_defaults.py and applied by runtime/sample_utils.py. Penalties and logit bias act on the request's target distribution on every route, including MTP, prompt-lookup and external-draft verification, where acceptance uses the same penalized distribution, so speculation stays exact. Since the page was written, a field the request leaves unset takes the model vendor's declared default instead of a fixed engine value, and each receipt lists which fields were explicit, filled from the profile, or neutral. The top-p nucleus is computed in float32 on every device, because a bfloat16 cumulative sum over a 248K vocabulary collapsed it on the CPU backend. Seeds are unsigned 32-bit, and a positive temperature must keep 1/temperature finite in float32. The card composes with Exact speculative sampling law and Vendor sampling defaults per model. Penalty defaults turn on the per-lane logits-processor path, which SERVING.md notes costs some decode throughput.

Field check

Applying model-recommended defaults is now common: vLLM's --generation-config defaults to auto, which applies the model's generation_config.json, and Ollama merged #16471 to honor model generation defaults. Sampling parity across execution paths is still being fixed elsewhere: Rapid-MLX merged #3496 in Sept 2026 so seed, top_k and min_p are honored on its media lane, and mlx-serve merged #433 and #434 reworking sampled MTP verification. mlx2 has no cross-engine measurement of sampled-output equivalence. Its claim is narrower: penalties and logit bias are applied inside speculative acceptance rather than bypassed.

Probability

Actual emitted-token log probabilities

Logprobs and up to eleven ranked alternatives are serialized for ordinary, accepted-draft and correction/bonus tokens in both response modes.

Scoring, confidence and audit consumers see the target distribution that produced the output—not the draft distribution.

How it works

token_logprob in logprobs.py builds each entry from the distribution of the token actually emitted: the normalized post-processor logits on ordinary decoding, and the transformed target verifier row on native MTP and external-draft routes, for accepted drafts and for correction or bonus tokens, never the draft or residual distribution. Up to eleven sorted alternatives are returned, and negative infinity is serialized as -9999 so the JSON stays valid. Since the page was written, entries also carry the token's UTF-8 bytes (018eacb), SentencePiece space markers are preserved (eb1d469), and Responses serializes the same data on response.output_text.delta events and in the terminal payload when include names message.output_text.logprobs (responses_logprob in openai_compat.py). Requests without logprobs do no extra device-to-host reads. scripts/qualify_serving.py has a required logprobs check comparing entry counts with completion tokens, and older receipts without it fail closed. This composes with Exact speculative sampling law and Persistent segmented self-MTP: speculative routes report the distribution they sample from.

Field check

Logprobs are widely supported, but the details keep moving. SGLang merged #38604 on 2026-09-19 to recover logprob token bytes from token ids for UTF-8 fragments, the same problem mlx2's byte field addresses, and merged #34776 to guard top-logprob keys in its completions echo path. mlx-lm's SERVER.md documents a logprobs count of top tokens, and llama.cpp documents n_probs. vLLM's DiffusionGemma fixes, #57414 and #57417, show that non-standard decoders need explicit rules for which step's probabilities are reported. mlx2 has not compared its numerical values against other engines.

Constraints

Regex, JSON object and strict JSON Schema

Canonical, bounded grammars scan candidate tokens in logit order, finish the tail exactly in a worker pool when possible and fail closed on empty continuations or budget violations.

Structured output is an execution constraint with a measurable tail bound, not post-hoc JSON repair.

Two mask defects were found and fixed on 2026-09-20 by a parallel session, and they compound. First, the grammar’s piece table was sized by the base vocabulary rather than the full token id space, so added tokens fell off the end of the table — and added tokens are exactly where tool-call markers like <tool_call> live, making them unreachable under any composed grammar (5484753, on main; an identical unmerged copy sits on branch claude/fix-grammar-added-tokens-20260920 at 41abb51). Second, _allowed_by_logit_order grows its examined frontier geometrically and carried start across rebuilds, which is sound only while logits are distinct; under exact ties np.argpartition picks an arbitrary representative, so a rebuild’s prefix could hold never-examined ids that were then skipped for good. Ranking by (-logit, id) gives a total order whose top-want prefix is stable as want grows (c623a20). The reproduction is worth stating plainly: on the real Flash-Next vocabulary, 248,320 wide, with an all-zero logits row and the Qwen XML tool grammar, the walk admitted <tool_call> alone and reported tail_mass_bound 0.0 — an exact mask that had silently dropped two ids a distinct-logit row admits. With the piece table also cut short, the same row admitted nothing at all. Severity, not overstated: served bf16 rows tie all through the tail, so the production effect was a mask narrower than exact rather than an outage. Cost of the fix is 0.12-0.39 ms per rebuild on that row, against at most a handful of rebuilds per constrained token.

The card describes the logit-order scanner, which is now only the fallback. The default engine is an exact token-level automaton with complete masks (tail_mass_bound 0.0). Later commits added bounded digit and whitespace runs, local $ref resolution, byte-fallback admission, one shared stop-token set and qualification-mode dead-end diagnostics. SERVING.md still lists both engines as not qualified on a served route.

How it works

response_format (json_object, strict json_schema) and raw regex grammar compile through compile_constraint in structured_output.py. The default engine is now structured_automaton.py: the pattern compiles to a minimized DFA, or a pushdown automaton for recursive json_object, capped at 20,000 DFA and 200,000 NFA states. A state's admissible-token mask is one walk down a vocabulary trie, memoized in a 64 MiB LRU; on the Qwen3.6 vocabulary compile takes 3-7 ms, a first state visit 1-4 ms and a repeat about 20 us. Masks are exact, so receipts report tail_mass_bound: 0.0; patterns outside the subset fall back to the logit-order scanner. Byte-fallback pieces are admitted through a UTF-8 tail (a GPU probe generated U+10FFFF in 7 tokens). JSON digit runs and whitespace are bounded, 19 integer digits and 32 characters, after GPU runs looped to the token cap. One frozen stop-token set is shared by all routes; the fix moved Laguna core checks from 35/4 to 39/0. It composes with Grammar deferral past thinking and Forced tool calls constrained by grammar.

Field check

Grammar-constrained decoding is mature on GPU servers. vLLM documents xgrammar and guidance backends with choice, regex, JSON, EBNF grammar and structural-tag constraints, and llama.cpp supports GBNF grammars and json_schema. Gaps are still being closed: vLLM's open #54442 stops structured requests sampling from an unmasked row, open #48416 and #57592 fix xgrammar feature-gate bypasses, and oMLX's #3321, open since Aug 30, bounds JSON-schema whitespace, the fix mlx2 landed in 735140d. Ollama merged #18105 enabling speculative decoding under structured output on its MLX runner. vLLM and llama.cpp accept richer grammar languages (EBNF, GBNF) than mlx2's regex and JSON subset.

Parallel output

n=1…8 atomic sampling cohorts

The whole cohort is reserved before publication; independent seeds branch from one attested APCv2 prompt boundary.

Multiple choices pay for one prompt when safe, while partial allocation and misleading “shared prefill” claims are rejected.

The per-sample headroom charge is now 2 GiB with a bounded 15 s wait before refusal; it was 4 GiB with an immediate 429.

How it works

n from 1 to 8 on a nonstreaming request creates independent sample jobs, each with its own seed and request state. Before any job is queued, admit_parallel_samples in serving.py checks the count against configured lanes and against measured physical headroom: the unchanged 20 GiB reserve plus 2 GiB per sample, which is the measured 1.76 GiB per-lane transient rounded up. Since the page was written it polls headroom for up to 15 s before refusing, because a 20x20 sanity run saw 14 of 20 n=2 requests on Flash-Next refused instantly with 429 while single requests under the same load simply queued (fc0a054). If any sample fails to attach, _fail_attaching_cohort fails the whole cohort, and SampleFailed returns the engine's own status. Samples branch from one APCv2 prompt boundary when that boundary is attested, so the prompt is prefilled once. The card composes with APCv2-only prefix reuse, Atomic multi-lane admission and uniform fallback, Physical memory accounting and Protected 20 GiB service/driver reserve.

Field check

Multiple choices per request are standard on GPU servers; vLLM's SamplingParams documents n as the number of output sequences per prompt. In the MLX projects searched I found no pr_index activity on n in the window checked, and I make no claim about whether they support it. The claim here is limited to mlx2's own behavior: it reserves the whole cohort against measured headroom before publishing any sample, waits a bounded time instead of refusing on one reading, and fails the cohort together rather than returning a partial set.

ResponsesNew

OpenAI Responses API with bounded state

/v1/responses runs on the chat lifecycle with typed SSE events, function tools, a tenant-scoped store, previous_response_id continuation and cursor-shaped input items.

Clients written for OpenAI's newer API, including stateful multi-turn loops, run locally without a second engine.

How it works

responses_to_chat_request in openai_compat.py validates the body against an explicit field set, maps instructions to a system message, max_output_tokens to max_tokens, reasoning.effort to reasoning_effort and text.format to response_format, then submits an ordinary chat job; responses_payload builds message and function-call items with usage and the route receipt. Streams emit typed events with monotonic sequence_number, and function calls are buffered through terminal contract validation before their argument delta and done events. With store (default true), ResponseStore in api_resources.py keeps payloads and replayable context per tenant, evicting least-recently-used entries past 128 entries or 32 MiB, and --api-state-dir writes each record atomically so it survives restart. GET /v1/responses/{id}/input_items reconstructs pages from stored context instead of keeping a second copy, so byte accounting is unchanged. Unknown fields and include values return 400. It reuses Function calls and Qwen tool parsing, Actual emitted-token log probabilities, Regex, JSON object and strict JSON Schema, and HMAC-signed reasoning replay.

ReasoningNew

HMAC-signed reasoning replay

Returned thinking blocks and Responses reasoning items carry an HMAC bound to model and tenant, and only verified reasoning re-enters the prompt on a later turn.

Stateless clients can hand reasoning back without letting a forged or cross-tenant trace steer the model.

How it works

ReasoningSigner in reasoning_signatures.py computes HMAC-SHA256 over canonical JSON of key id, kind, model, tenant and text. Anthropic thinking blocks get mlx2.thinking.v1.<key_id>.<mac>; Responses reasoning items get mlx2.reasoning.v1.<key_id>.<payload>.<mac>, where the payload is the base64 text so a store:false client can replay it. The token is signed, not encrypted, and the docs say so. On the next turn, anthropic_request_to_chat and _responses_messages verify each signature with hmac.compare_digest: verified text becomes reasoning_content, while unverified, cross-model or cross-tenant blocks and redacted_thinking are dropped and counted in reasoning_signature_rejections. Keys come from --reasoning-signing-key-file, with a warning if permissions are broader than 0600, or --reasoning-signing-key-env; without either, a random per-process key is used and signatures do not survive restart. Reasoning items appear only when include asks for reasoning.encrypted_content. It serves Anthropic Messages endpoint and OpenAI Responses API with bounded state, and Official OpenAI and Anthropic SDK smoke covers the round trip.

Field check

Reasoning replay for stateless clients is recent everywhere. SGLang merged #38690 on 2026-09-12 so reasoning.encrypted_content is populated and restored on replay; its description says the blob is encoded, not cryptographically protected, and lists server-side key management as out of scope. vLLM merged #44301 for an include_reasoning parameter on non-Harmony models. OpenAI's hosted API returns encrypted reasoning, which a local server cannot reproduce without its own key. SGLang #38690 explicitly says its replay blob is encoded rather than cryptographically protected; mlx2 authenticates its own replay blobs. This is not a survey of every server.

LimitsNew

2M-token caps with prompt-aware default

Explicit output caps accept up to 2,097,152 tokens and are never clamped; an omitted cap resolves to the smaller of --default-max-tokens and the remaining context.

Long generations need no guessed cap, and operators can trade the default length for admission width.

How it works

resolve_output_limit in request_limits.py serves every dialect: Chat max_tokens and max_completion_tokens, Responses max_output_tokens, Hermes options.num_predict and Anthropic's required max_tokens all reach it. An explicit cap from 1 to 2,097,152 must fit with the prompt inside the effective context or the request fails; it is never silently shortened. An omitted cap becomes min(--default-max-tokens, context minus prompt), and the flag defaults to 65,536, so any request that fit the old 512-token default still fits. Receipts report the effective max_tokens and max_tokens_defaulted, and /v1/status.settings.default_max_tokens shows the setting. Admission reserves the whole default up front: SERVING.md's CPU projection for Flash-Next on a 128 GiB host shows admitted lanes falling from 16 to 6 for a 2K prompt and from 6 to 3 at 64K, compared with a 512 default. Explicit thinking_budget is bounded independently to the same ceiling. It feeds Physical memory accounting and Deferred memory admission without lane capture.

Field check

Engines differ on what an omitted cap means. llama.cpp's server README documents n_predict defaulting to -1, meaning unbounded. Ollama's open #17566 describes Cline sending num_ctx 128000 with num_predict 32000, and a thinking level equal to that cap consuming the whole response with no answer. Anthropic's Messages API requires max_tokens, and mlx2 keeps that rule. I found no evidence about other MLX servers' default caps and make no claim about them. mlx2's cost for a large default is admission width, which its docs quantify rather than hide.

Reasoning models can finish a formed answer instead of being cut off mid-thought. The mechanism ships and is unit-tested; it currently has no valid quality measurement.

Correction (2026-09-20). This card previously claimed that on North-Mini-Code 20x20 sanity rose from 394 to 399 of 400 with 18% fewer tokens, and that a 13-prompt experiment went from 10/13 to 13/13. How it works

SteeringNew

Calibrated commit-direction steering

While a lane reasons, a residual direction calibrated on the served artifact's own closed traces is added after one decoder layer, pulling run-on reasoning toward its close.

Re-measured on North-Mini-Code's corrected body, the held-out grid closes every prompt at 16/16 correct on 69% fewer reasoning tokens: 2,404 against 7,683 unsteered, which scored 14/16.

Correction (2026-09-20). The earlier 83% figure, and the claim that a same-norm random direction did worse than no steering, were measured before North's normalization was fixed and are void. On the corrected body the direction was recalibrated - peak cross-trace consistency moved from layer 28 to layer 32, +0.518 - and the grid re-run: shipped L32 alpha 0.2 scores 16/16 on 2,404 reasoning tokens, unsteered scores 14/16 on 7,683, and the same-norm random control scores 15/16 on 7,169, marginally better than off rather than worse. The defensible claim is therefore the weaker one: a random direction on the same schedule does not shorten reasoning, while the calibrated one does. It is no longer evidence that a wrong direction actively harms.

How it works

extract_directions in thinking_calibration.py computes, per layer, the mean residual over the last 24 in-think tokens before the close marker minus the mean over an early reflection window. ThinkingGuard.residual_steer supplies alpha * rms_L * v_hat for each reasoning lane; a batch gets one [B,1,D] tensor with zero rows for unsteered lanes, which a unit test shows stay bit-identical. artifact_identity hashes config, tokenizer, chat template and sampled weight bytes, and resolve_direction loads a direction only for that identity. Without one, auto_calibrate runs for about two minutes at startup and stores a result only if its gates pass: 10 or more closed traces, consistency of at least 0.30, no lost accuracy or closes, shorter reasoning, and a random control that does worse. Otherwise steering stays off, or startup fails if --thinking-steer-alpha was explicit. The saving is concentrated where it should be: the run-on prompts fall from 6,666 to 1,536 reasoning tokens while the hard problems are barely shortened, 862 to 723, and stay correct, so alpha 0.2 is not truncating thought. The serving-level claim that once sat here - 20x20 sanity at 400/400 with 44% fewer completion tokens - is void with the rest of the pre-fix North campaign and was not re-run. It runs on the ordinary route and prompt-lookup verify only, and steered lanes skip exact APCv2 stores. It extends Thinking budgets and run-on release.

Field check

Other servers control reasoning length at the token level. llama.cpp's reasoning budget can inject a wrap-up message before forcing the end tag, vLLM documents thinking_token_budget, and Ollama's open #17566 measures wrap-up messages on Gemma 4 and Qwen3.6 and finds the effect depends on the model. Those approaches do not require mlx2's residual-direction calibration and apply to supported thinking-tag templates, which is a real advantage. mlx2's steering needs residual taps and a calibrated artifact, ships for North-Mini-Code only, and does not run on native MTP or external-draft routes.

An APCKey binds model, revision, adapter, tokenizer, cache-layout and semantic fingerprints (media, and tenant when scoped); a PromptTrie radix index maps token paths under that key to frozen entries, and _lookup_locked returns the deepest exact match with a hit kind or an explicit miss reason. inspect_apc_capabilities classifies each concrete cache as kv, rotating_kv, mixed_rotating_kv or checkpointed_hybrid and decides whether arbitrary branching is lossless. ServingEngine._publish_checkpoint is the single store path, so idle spill, persistent blocks, capsules and sessions all derive from stored entries, and approximate state is refused there. The measured effect is skipped prefill, not faster decode: the Flash-Next qualification recorded a 16,352-token hit on a 16,353-token prompt (docs/RESULTS.md). Layered copy-on-write branches, Atomic target + draft snapshots and Exact interior hybrid checkpoints all build on this one index.

Checksummed persistent APC blocks

How it works

How it works

--apc-persist-dir turns APCv2's idle-spill format into a restart-surviving tier. Each exact entry is written as target, draft and aux safetensors files plus a JSON manifest (_manifest_for_entry) holding the APCKey, the token path and its SHA-256, retention role, session tags, pins and an identity digest bound to native runtime identity; files are fsynced and the directory is locked to one process. At startup _rescan_persisted_entries reads only manifests, discards unknown schemas and identity mismatches, and quarantines or deletes corrupt entries within --apc-quarantine-max-* bounds. Restore always verifies SHA-256. --apc-persist-on-shutdown parks entries within a time budget, and the loopback admin suspend spills every resident entry. CPU qualification spilled 8 GiB at about 1.9 GiB/s, rescanned 64 manifests in 18.7 ms with zero payload reads, and restored a verified 1 GiB entry in 435 ms (qualification/runs/apc-persistence-cpu-20260918). A profile selecting persistence must observe write, rescan and restore across processes. It underlies Tenant-owned APC sessions.

Field check

How it works

The ordinary and self-MTP routes run one BatchGenerator (runtime/generate.py) whose lanes are inserted and removed between scheduler cycles, so a request can join or leave a live batch without waiting for it to drain. Prefill

Adaptive, bounded prefill

Chunk sizes respond to workload and contention while remaining inside configured and measured limits.

Long prompts stop monopolizing the generation loop.

How it works

Prefill runs in slices. The serving engine constructs BatchGenerator with adaptive_prefill=True on the ordinary and self-MTP routes. At each decode boundary, _adaptive_prefill_decision picks a chunk from the slice ladder (64, 128, 256 or 512, capped by prefill_step_size). _measured_adaptive_prefill_chunk chooses the largest slice whose EWMA per-token prefill cost fits in 75% of the 1,500 ms inter-token target, minus the last decode duration. If the last decode interval already exceeded the target, prefill is deferred. After 2,000 ms of waiting it is forced at the smallest slice, so a long prompt cannot be deferred forever. "Wall-time decode debt" then clamps that chunk. The adaptive_prefill_chunk_histogram and slack- and deadline-forced counters show which path ran. "Short prompts overtake long prefills" (new since the page was written) adds one-chunk interleaving on top. Prompt-lookup and external-draft routes keep fixed prefill steps. The Qwen3.6-35B window in commit 49d1de3 is where this ran on GPU.

Fairness

Wall-time decode debt

Contention-aware prefill caps measure stall cost and repay it with decode time rather than counting requests as if they cost the same.

Interactive generations keep making progress beside expensive prompt ingestion.

How it works

DecodeTimeFairness in runtime/adaptive_policy.py is a host-only controller that owns no model state. When prefill runs while decode lanes are active, observe_prefill adds fair_share × elapsed seconds (0.5 by default) to a debt. While debt remains, may_prefill refuses further prefill, and observe_decode pays the debt back with measured decode time. cap() limits contended chunks to what the best observed prefill rate completes within stall_target_ms (500 ms). The limit is rounded to a 64-token grid with a 64-token floor. It uses a running maximum, so a slow contended sample cannot shrink the cap in a feedback loop. Costs are counted in seconds, not requests, so a long prompt pays for the stall it causes. decode_time_fairness_policy enables it on the ordinary and self-MTP routes. The Qwen3.6-35B GPU window (commit 49d1de3) recorded 63 capped chunks, 113 deferrals and 176 repayments under contended 19K prefills. It supplies the cap used by "Adaptive, bounded prefill".

Field check

Protected host-scaled service/driver reserve

Corrected again on 2026-09-19 (40821a3). Scaling by physical RAM assumed the OS withholds a fixed fraction. Measured, it does not: a 128 GiB host advises 112.00 GiB and withholds 16.00 GiB, 12.5%, while a 36 GiB M3 Pro advises 28.08 GiB and withholds 7.92 GiB, 22.0%. The old rule was therefore wrong by 76% on the M3 Pro, and it charged the margin a second time on top. The live symptom: Muse-Glimmer-30B with its DFlash2 drafter at 21.56 GiB resident left 6.14 GiB of advisory residue, of which the 5.625 GiB reserve left 0.52 GiB, so serving 429’d on a two-thirds-empty machine. The reserve now keys on the advisory itself, and tests/test_host_scaled_reserve.py pins the 128 GiB calibration host bit-for-bit so the recalibration cannot move it. Landed by a parallel session, not the roadmap campaign.

How it works

SelfMTPLaneAdmissionController (runtime/memory_policy.py) defines hard_reserve_gib as a service reserve (12.5% of physical unified memory, capped at SERVICE_RESERVE_GIB = 16 GiB and floored at 3 GiB) plus a driver allowance (3.125%, capped at DRIVER_ALLOWANCE_GIB = 4 GiB, floored at 0.75 GiB). The caps and fractions are the same number on the 128 GiB calibration host, which still reserves exactly 20 GiB; a 36 GiB M3 Pro reserves 5.625 GiB and anything at or below 24 GiB reserves the 3.75 GiB floor. Held flat, the 20 GiB absolute was fatal off the calibration host: with Metal advising 28.08 GiB on a 36 GiB M3 Pro, a 16 GiB model leaves ~11.5 GiB, under the reserve, so every request 429'd before a lane was costed and the constructor rejected any smaller value. Since 40821a3 the fractions key off the Metal advisory rather than installed RAM. Keying on physical RAM charged the OS margin twice, because the advisory has already withheld it: the reserve is now clamp(3.0, 16.0, advisory - 0.75 * host) with a clamp(0.75, 4.0, advisory * 4/112) driver allowance. decide() computes usable memory as free minus that reserve before placing any lane. Lanes are then charged at 0.44 GiB per 1K tokens of context plus a 1.76 GiB depth-2 verify transient. The degradation order is the largest k=2 subset, then k=1, then one plain lane, then queue. SATURATION_LANE_CAP=16 bounds width even when memory is plentiful, because a dense 27B measured 270 tok/s aggregate at N=16 and 52 tok/s at N=40. The same reserve is subtracted from execution headroom in serving.py and charged by admit_parallel_samples; the host size is probed once at server start and injected, so the policy module stays pure. Since fc0a054 that guard adds 2 GiB per sample, down from 4 GiB. At Flash-Next's 72.5 GiB resident point on a 128 GiB host, the reserve leaves 35.5 GiB for lanes. It is the floor under "Physical memory accounting".

Reclamation

Optional work yields before useful state

Promotion is settled, canceled and drained before checkpoint eviction; accounting is remeasured and never credits hypothetical freed bytes.

An optimization cannot destroy the warm prefix it was meant to accelerate.

cb7921e extends this to APC interior checkpoints: optional positions are charged once, and the ones that do not fit are dropped and counted instead of rejecting the request.

How it works

Optional work gives way before useful cache state is touched. An asynchronous physical-QSA promotion reports its reserved future bytes as pending_bytes until settle_for_admission() synchronizes it. The pressure preflight uses a side-effect-free admission preview and then settles and remeasures. If pressure remains, it cancels and drains the promotion before any reclaim or APC eviction. A drain failure propagates with the ticket still owned. A bounded grace period of at most 2 s, retried every 250 ms (optional_reclaim_wait), keeps warm APC entries while accounting recovers. execution_headroom never credits bytes that have not been measured as freed. A ceiling plan tells real memory pressure apart from a lane-count cap, so a capacity limit does not trigger cancellation. Since cb7921e the same rule covers interior checkpoints: each selected position is charged once, and positions that do not fit are omitted and counted. The design came from a 262K warm-prefix miss (docs/experiments/PROMOTION-PRESSURE-REVIEW.md). It protects state for "APCv2-only prefix reuse".

Cohorts

Atomic multi-lane admission and uniform fallback

Tenant/cohort identity, whole-cohort staging, uniform lower draft depth and transactional rollback prevent partial-width execution. When the contract cannot be met, the cohort fails together.

7daf236: declared cohorts now stay atomic through incremental (sliced) self-MTP prefill. A member that reaches its final token is held until its siblings are ready, and a batch that would include only part of a cohort fails closed.

How it works

A client declares batch_cohort. ServingEngine stages the members until all have arrived, bounded by batch_cohort_timeout_ms (1,000 ms by default), and then publishes them as one atomic group. SelfMTPLaneAdmissionController.decide(atomic_cohort=True) requires every eligible lane to fit at one uniform draft depth. It tries maximum k and then lower k, and otherwise queues the whole group. It never admits a subset. CohortAdaptiveMTPDepth ("Cohort-wide MTP depth control") makes one depth decision per physical cohort. Depth 0 is a temporary exact ordinary round with periodic depth-1 probes. Failures surface through take_atomic_cohort_failures, and every member gets a 429 together (batch_cohort_jobs_failed_closed). Since 7daf236, _advance_mtp_prefill holds a member that reaches its final token (atomic_cohort_prefill_holds). _make_mtp_batch now fails closed before popping a prefix that holds only part of a cohort, so B1 decode cannot start while a sibling is still queued. Admission that avoids false 429s

Parallel samples, warm hits and optional checkpoints are charged at measured cost. Admission waits or reclaims allocator memory before it refuses.

How it works

Four corrections to admission estimates landed since the page was written. First, admit_parallel_samples used to charge 4 GiB per sample and refuse instantly. Exact speculative sampling law

Accepted proposals, rejection corrections and bonus tokens use transformed target probabilities with explicit rollback and synchronization.

Acceleration does not quietly substitute the draft model's distribution for the target model's contract.

How it works

verify_proposals in speculative_sampling.py is the reference rule for sampled speculation. The target law p already includes request temperature, top-p, top-k, min-p and history processors, and every law is checked before any draw changes RNG state. The caller commits the anchor plus accepted inputs atomically and leaves the correction or bonus token pending. CommittedRecoveryCheckpoint in committed_recovery.py (300a7e7) gives the PLD, external-draft and self-MTP routes one request-private checkpoint, taken only at a proven committed boundary. verify_sync.py traces where verification forces a GPU sync. The DFlash2 CPU suite checks the residual law empirically over 12,000 draws. "Opt-in FLy relaxed verification" is the only departure, and it is off by default. The rule serves "Persistent segmented self-MTP", "Prompt-lookup decoding" and "Muse DFlash2 linear speculation".

A route is selectable only when its model declares the capability and a matching profile satisfies capability, fidelity and evidence requirements.

How it works

Observed use

Mechanism counters and route receipts

Responses and status expose route identity, cache reuse, MTP acceptance, actual widths, structured-output bounds and kernel engagement/decline reasons.

Operators can distinguish enabled, eligible, selected and executed.

A parallel session populated per-round verify histograms on every speculative route on 2026-09-20 (daf332a). verify_span_hist was declared on the shared prompt-lookup base but written only by the prompt-lookup route, so self-MTP receipts carried an empty dict and the external-draft route had no equivalent at all; both now write one entry per committed cycle. The addition that earns its place is verify_accept_hist, accepted speculative tokens per round, on all three routes: because a draft accepted to depth k would also have been accepted under any shallower cap, tau(k) = mean(min(a, k) + 1) falls out of a single deep run by truncation, with numerator and denominator drawn from the same run instead of two runs whose noise compounds. The span histogram cannot do that. Both are host integer counters bumped from values already on the host — no device work, no eval, no readback — costing about 39 ns per round against a verify round measured in milliseconds, which is why they are unconditional rather than gated, and a deterministic CPU run is byte-identical to the parent commit once the new keys are removed.

How it works

RuntimeTelemetry in src/mlx2/telemetry.py is a bounded, lock-guarded event ring with a capped counter map. Once the map is full, new event names fold into __other__, so it cannot grow without bound. Engine, scheduler and execution modules emit named events for engagement and decline: segmented-MTP transactions, prompt-lookup rotating replay, fused GDN, indexed QSA, APC interior checkpoints and self_mtp_zero_fast_rounds. Every completed generation carries an mlx2 receipt with the route, cached-token and observed-width data, plus MTP acceptance when MTP executed. The counters are host integers with no device sync, so they stay on by default. Security posture

Hostile-request hardening

Input envelopes, output limits, finite numeric checks, vocabulary bounds, bounded stop lists, contained cache paths and strict JSON parsing constrain abuse.

The local server has explicit resource and parser boundaries even before an authenticated front end.

How it works

validate_request in src/mlx2/server.py and the helpers in request_limits.py and openai_compat.py check each request before it reaches the engine. The input envelope is context-derived and bounded at 2 to 32 MiB. Nonstreaming requests allow at most eight choices. max_tokens is bounded at 2,097,152, and an explicit overflow is rejected rather than clamped. When max_tokens is omitted, admission charges min(--default-max-tokens, remaining context), with a default of 65,536. Numbers are checked with math.isfinite, and JSON parsing refuses NaN and Infinity constants through parse_constant. Schema values are validated recursively, stop lists are bounded, and cache paths stay contained. Admin endpoints for quiesce, resume and state accept only loopback clients and, with --admin-token-file, also require a token. Their bodies are validated too, for example a drain timeout between 0.1 and 3600 s. The server binds to loopback by default. Memory admission in "Physical memory accounting" remains a separate, tighter bound, and rejections are counted in mlx2_admission_decisions_total.

Field check

vLLM's security guide says --api-key protects only the /v1-style prefixes. It notes that operational endpoints such as /pause and /abort_requests are unauthenticated, and it recommends a reverse proxy allowlist. Its resource caps are environment variables such as VLLM_MAX_N_SEQUENCES (default 16,384) and limits on media size and duration. llama.cpp exposes /health without an API key by design. mlx2 has a similar stance (loopback by default, with an authenticated front end required for remote use), and its per-request caps are tight by default (for example at most eight choices per request).

Prefill chunk size recorded in the receipt

How a prompt was sliced during prefill is part of the answer it produced, so a result that will not reproduce can be traced to the slicing rather than argued about.

At 16K on Qwen3.8-27B, a bit-for-bit repeat agrees 1.000 with KL exactly 0, while re-slicing the same prompt at chunk 4096 moves a logit by up to 7.55 and disagrees on 1 of 128 top-1 tokens.

How it works

Roadmap item rm15. Receipts carry a prefill_chunk block, schema mlx2.prefill-chunk-trace.v1, with configured_step, adaptive, adaptive_slices, widths, rounds, first, last and varied, plus the counters prefill_chunk_rounds_recorded and prefill_chunk_varied_requests. The measurement behind it (qualification/runs/rm15-chunk-variance-20260920/, Qwen3.8-27B-oQ4e-mtp) scores every arm against a single-chunk unchunked reference. At 4K over 128 scored tokens: the unchunked repeat gives top-1 agreement 1.0, KL 0.0 and max absolute logit delta 0.0, which is the determinism control passing; chunk 2048 gives 0.9922 / 7.653e-4 / 0.797 and reproduces digit for digit on a repeat; chunk 1024 gives 0.9766 / 9.045e-4 / 0.4375. At 16K over 256 scored tokens: chunk 2048 gives 0.9844 / 7.093e-4 / 3.6875, chunk 1536 gives 0.9922 / 6.968e-4 / 3.1875, and chunk 4096 gives 0.9922 / 6.668e-4 / 7.5547. Every arm differs from the reference in 127 cache fields, with the first divergence at L0.gdn at 0.0009765625 — two to the minus ten, one bf16 unit in the last place. The finding is therefore not that chunking is wrong but that it is a parameter of the answer, and the receipt is where it belongs. One correction this card records against the lab’s own docs: docs/SERVING.md currently attributes top-1 0.891 and max delta 6.4 to this experiment, but those are rm07’s control-arm numbers on a different corpus, and rm15’s own page says its predecessor’s top-1 figures were not reproduced, only the phenomenon and its magnitude.

Chunked prefill is standard and its numerical consequences are usually left implicit; the claim here is narrow and about bookkeeping rather than about being more deterministic than anyone else. The cross-experiment discrepancy above is exactly the kind of thing a receipt field exists to settle. No competitor documentation was surveyed for this card in this pass, so no comparative claim is made here.

What is hardest to copy

The moat is the composition.

Individual kernels can be reimplemented. The harder asset is the set of boundaries that lets many advanced mechanisms coexist without lying about correctness, memory, or execution.

M01

A single state constitution

APCv2, request revisions, fidelity and plane identities cover warm reuse, speculation, rollback, spill, surgery, compaction and future approximation.

M02

Hybrid architecture depth

PLE, QSA, GDN, MoE and MTP are optimized as interacting parts of one model, including their memory geometry and rollback semantics.

M03

Receipts all the way down

The API result can be connected to scheduler decisions, cache reuse, actual width, speculative acceptance and kernel counters.

M04

Failure as a product feature

Partial fanout, unsupported fidelity, stale revisions, unobserved mechanisms and memory shortfalls are designed outcomes—not undefined behavior.

M05

Provenance without dependency drag

Proven ideas are mined mechanism by mechanism, attributed and adapted, while the production core stays independent of research checkouts and replaced products.

M06

Institutional memory in code and evidence

Negative experiments, automatic-selection gates and mechanism-specific tests prevent benchmark folklore from becoming defaults.

The claims we should not make

  • Not “faster than every inference stack.” Hardware, models and workload domains differ.
  • Not “more features than vLLM/SGLang.” They have much broader distributed and accelerator ecosystems.
  • Not “exact everywhere.” kv_q8/kv_k8v4 KV quantization sits behind the approximate-KV state seam, and int8 prefill and FLy verification are separate opt-in approximate-fidelity execution routes; no TurboQuant math is claimed.
  • Not “concurrency equals model batching.” mlx2 reports observed compute widths precisely because it does not.
  • Not “configuration proves acceleration.” Selection and observed-use remain separate even under this release's accepted-feature assumption.
  • Not “speculation always wins.” Separate runs show the repaired 35B self-MTP at 135/217 tok/s (1/4 lanes) against an earlier ordinary run at 130/287; these are orientation numbers, not a matched winner comparison.
  • Not “bit-identical across kernels.” The NAX small-M verify kernel is deterministic but rounds differently from qmv_wide, so greedy outputs at four lanes can diverge from the scalar path.
  • Not “North’s past numbers still hold.” Until 2026-09-20 mlx2 served North-Mini-Code with nn.LayerNorm(eps=1e-5) where the checkpoint specifies RMSNorm(eps=1e-6), on all 49 decoder norms and the final one. The corrected body does not generate the same greedy text, so every North quality, acceptance and grading number measured before 2026-09-20 is void, and this page no longer quotes any of them. North had also never passed a serving qualification: of the five machine records the lab held, three were passed=false or aborted and the two green ones were produced on the wrong body. On the corrected body the ordinary route passes 30 of 30 checks — the first valid North qualification (qualification/runs/north-requal-20260920/, commit 3e97f60; the void list is that run’s INVENTORY.md).
  • Not “benchmarked by third parties.” mlx2 has not been run through SiliconBench or any external harness yet.
  • Not “a remote-secure public endpoint.” The built-in listener is loopback-first and needs an authenticated front end for remote exposure.
