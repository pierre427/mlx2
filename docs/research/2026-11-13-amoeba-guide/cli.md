# `mlx2 amoeba`: the mapping workflow as one command

*2026-11-16. Experimental and unqualified (`mlx2.experimental.amoeba`). Phases 1–2: the command, the resource
plan, receipts and resume, progress and build-time metrics. Phase 3 (the bundle loader, `mlx2 serve
--amoeba-bundle`, per-stream gating and serving metrics) is not built yet.*

The procedure is [mapping-workflow.md](mapping-workflow.md), the foundation document. This command runs it
for any model the carve host loads, so that each session stops writing its own per-model scripts.

```bash
mlx2 amoeba plan --model ~/mlx-models/<artifact>
```

```bash
mlx2 amoeba build --model ~/mlx-models/<artifact> --out ~/amoeba-runs/<artifact>-<rev>
```

```bash
mlx2 amoeba status --out ~/amoeba-runs/<artifact>-<rev>
```

```bash
mlx2 amoeba resume --out ~/amoeba-runs/<artifact>-<rev>
```

Each stage also runs on its own, for example `mlx2 amoeba boxes --out DIR` or `mlx2 amoeba gates --out DIR --redo`.
`inspect` prints the model's identity and layout without loading weights.

## What runs

| Stage | Workflow step | What it does | Research code it runs |
|---|---|---|---|
| `core` | 2 | Writes on-policy continuations of the English prose (1 greedy + 3 at T=0.7). Carves the joint core mask (KL to the full model, layer-wise gradients; the export cut is chosen on the carve's spare split, and there is no bisect on held). Runs the English-only check: held non-English probes and held English, core alone versus full. | `scripts/amoeba_onpolicy_gen.py`, `python -m research.amoeba.carve`, `child_probe corecheck` |
| `map` | 1 | Captures each unit's activation peak on every probe window (fit and held). Clusters the **non-core** units by co-firing on fit (virtual experts per layer, then global spherical k-means, k = 50–130 by size). Tags clusters against twin and shuffled-label controls. Runs after `core` because step 1.2 clusters the non-core units. | `child_capture` (the topic-capture format) → `scripts/amoeba_map_cluster.py --exclude core` → `scripts/amoeba_topics_label.py --core` |
| `boxes` | 3 | Makes one box per language and per subject branch, plus one per untagged cluster. Writes continuations of each box's carve, val and held prompts. Carves every box with the core fixed, in one model load. The size is chosen on val documents at +0.03. The held check runs once. A same-count random box is the control. | `scripts/amoeba_fn_boxset_build.py`, `child_boxbatch` (generalised `amoeba_fn_boxbatch.py`) |
| `partition` | 4 | Applies the table: core or 3+ boxes → core; exactly 2 → a cross-box tile for that pair; exactly 1 → that box; none → a remainder tile per map cluster. Checks that the cover is exact. | `stages.run_partition` |
| `gates` | 5 | Trains one detector per box on the residual stream entering layer L/4, using fit probes (its topic against everything else). The threshold is chosen on fit only. Reports the held false-open and miss rates. | `child_probe gates` |
| `bundle` | 6, §10 | Writes the tiles, gates, map, taxonomy and probe manifest. Writes the prompt set as Parquet plus a manifest, covering every map, core and box text with its origin and licence. Writes registry entries, and a manifest with sha256 for every file. | `scripts/amoeba_prompt_set.py` (now also `--capture-run`) |

Model work runs in child processes, one model per process. Nothing here branches on a model name. The carve unit
comes from the artifact: MLP neurons for dense layers, and neuron units by default for MoE layers (`--moe-units`).
The map captures MoE layers in expert units, because a neuron-unit capture would be tokens × E × F. Every neuron of
an expert takes that expert's cluster, and an expert counts as core in the map only when all its neurons are core.
The file-backed PLE assertion turns on when the artifact ships `ple_rows.bin`.

## Fixed data defaults and verdicts

The data rules in workflow section 4 are fixed in `config.DATA_DEFAULTS`:

- 128-token windows, two per document, at seeded random offsets;
- shared templates stripped (more than 20% of a topic's rows);
- code documents cut at their first line of code (`prog.*` boxes);
- continuations from a 96-token mid-document prompt: 64 new tokens, 1 greedy and 3 at T=0.7, with recorded seeds;
- the carve scores the continuation plus the last 32 prompt tokens;
- held text is never generated by a model and never chooses anything.

To change a data rule, pass `--data-override KEY=VALUE --override-reason "..."`. The reason is recorded in every
receipt.

A **profile** changes compute only: steps, sequence counts, prompts per box and probe subsampling. `full` uses
the values the Flash-Next runs used. `quick` is a pipeline check, never a box-quality claim, and its bundle says so.

A box **passes** when core plus box is within +0.05 nats of the full model on held text, and at most 0.5× the held
dCE of a same-count random box. The held dCE is pooled over the probe windows and the 1 greedy : 3 T=0.7
continuations, by row count. A box **misses** otherwise; the reasons are recorded in `boxes/next-round.json`. The
fix is better data for the next round, never a wider target or a cut against held. A box **fails** when the §7 per-box gradient check refuses it (`failure: gate-refused`, with the failing cells), and the build goes on: its units stay unclaimed and become remainder tiles, and its registry entry says so. A crash in a carve (anything but a gate refusal) stops the stage, so that resume retries it; the build also stops when every box is refused. A box is **covered** when its carve keeps no units beyond the core. Every box records the core-alone dCE on its validation documents as a diagnostic; it never skips a carve, because Pierre wants more boxes rather than fewer (mapping-workflow at 77d3442e9).

A cluster counts as tagged for box selection by its fit-split gates only (d ≥ 0.8 and ≥ twin95 + 0.5 on fit). The
held-confirmed labels in `labels.json` are the tagger's check and choose nothing. `next-round.json` reports the
median val→held gap over the boxes and the val target for the next round (+0.05 minus that gap); pass it with
`--compute val_target_nats=X`.

Untagged-cluster boxes take their carve and val documents from the fit probes the cluster responds to most. Their
held documents are the held probes of those fit probes' primary topics, so held text is chosen by topic labels and
never by the held responses of the units under test. Each box's generation prompts get their own domain, so rule 2
judges shared templates per topic. A document that several boxes chose gives its continuations to each of them.

## Resource plan

`plan` (and `build`, before anything runs) estimates the resident weights and each job's working set:

- carve: recorded layer inputs, logits, one layer's tape and the mask optimiser;
- capture and gates: per-layer responses.

The default cap is 80 GB, or physical memory minus 15 GB if that is lower. A cap over 80 GB needs
`--cap-reason`; Flash-Next carves use `--cap-gb 92 --cap-reason "Pierre 2026-11-15"`. The plan halves the batch
until a job fits in 90% of the cap. It **refuses** when batch 1 does not fit, or when the weights alone do not
fit: a model that needs layer streaming has no streamed backward pass yet. The child processes run the carve's
own footprint watchdog at the cap.

## Models that don't fit: rolling layer-window capture

This is the procedure in mapping-workflow §8 (Pierre, 2026-11-16). When the resource plan finds that the resident
load won't fit under the cap, it picks `--stream rolling` automatically and records why in the plan receipt
(`plan.stream`). `--stream rolling` forces it, which parity runs use. `--stream resident` never streams, so a model
that doesn't fit refuses. There is never a silent resident load over the cap.

- **What runs** (`child_rolling.py`): one layer-major driver over the sweep family interface
  (`research/amoeba/sweep/README.md`, v1), the maps session's contract.
  - `--family host` (`research/amoeba/sweep/host_family.py`) serves any **dense** model whose adapter accepts a
    weight-streaming request. The adapter's own `dense_layers` loader streams whole decoder layers; layer 0 stays
    resident.
    - Each layer is held under one acquire of the stream manager for all its batches, so it is read once per
      chunk; the receipt's stream counters show this.
    - Models whose layers return tuples or pass state between layers (Gemma4, HySparse2, shared-KV trunks) refuse:
      they need a sweep family of their own.
  - **MoE models too big for memory need a sweep family.** mlx2's loaders have no whole-layer expert streaming:
    `dense_layers` refuses routed experts, and `moe_experts` is an on-demand per-expert cache sized for decode,
    which would re-read most experts on every capture batch. The plan refuses such a model rather than re-reading.
    `rolling-parity --rolling-resident` checks the layer-major schedule on an MoE model that fits.
  - A checkpoint whose adapter family is registered in `research/amoeba/sweep/family.py` (`deepseek_v41`,
    `mimo_v2`, and later ones such as glm5_next) runs that family instead, with its own loader.
  - Either way the driver does the same:
    - each layer runs over every batch once, updating the corpus state, so each weight is read once;
    - the next K layers' checkpoint bytes are read into the page cache (the host family exposes
      `prefetch_ranges`), so disk reads overlap compute;
    - no KV cache and no APCv2; the host family recomputes each layer's call arguments (mask, per-layer inputs
      such as PLE) from the token ids with the model's own trunk;
    - dense |act − mu| peaks are finished exactly after the pass, from per-text max and min plus the fit mean;
    - the output is the same capture format.
- **The state:** the corpus state stays resident (`carry resident`). If it doesn't fit beside the window, the
  corpus is cut into the fewest chunks that fit, each one more read of the weights. When that would take more than
  two chunks, the plan instead keeps the state on disk between layers, using the sweep's `LayerState`
  (`carry memmap`), so the weights are still read once.
- **What it chooses:** K, the layers read ahead, comes from free memory: what is left under 90% of the cap after
  the resident remainder, three streamed units and the state. `--window K` overrides it, and refuses if it doesn't
  fit.
- **A map-only build:** a model that needs rolling capture runs the map stage only. Its units are clustered
  without a core, as in the maps campaign. Carve stages (`core`, `boxes`, `extract`) refuse, because the streamed
  backward pass is not built yet. A plan for such a model also refuses when:
  - its adapter accepts no weight-streaming request and has no sweep family;
  - its checkpoint has no `layers.<i>.` byte map;
  - the resident remainder plus three units doesn't fit.
- **A fresh parity gate on every run:** before the pass, one batch of 3 texts, cropped to a common length, runs
  through the schedule and through the family's ordinary `reference_logits`, over all layers (one weight read on
  each side). The run refuses unless the
  logits are bitwise equal, or within rel 1e-3 with top-1 agreement 1.0 (the sweep `parity_check` exact
  criteria). The result is written to `parity.json` and `meta.json`.
- **MoE map units are neurons** (`e*F+f`, as the carve's units, §3): the per-text peak of |w·h| over the routes
  that chose expert *e*, where h is the expert's intermediate activation. `--moe-units expert` maps whole experts
  (w·‖row‖). A neuron-unit map is large on disk (texts × E × F × 2 B per layer), so the map stage refuses before
  starting when it wouldn't fit in 80% of the free disk.
- **Parity across a model family (§8 item 7):** before trusting rolling capture on a new family, run
  `mlx2 amoeba rolling-parity --model <a model that fits> --out DIR [--carry memmap]`. It runs the resident capture
  and the streamed rolling capture on the same seeded texts, and compares every response, mu and the NLL. It passes
  when every layer's responses are within one fp16 ulp of that layer's scale and the NLL is within 1e-4; bitwise
  equality is reported separately. On Qwen3-0.6B (CPU, resident carry with 2 chunks and memmap carry): responses
  max-abs 0, NLL 5e-7.
- **Metrics:** each layer of each chunk emits a `layer` event (load s, compute s, prefetch stall s, state bytes,
  bytes read ahead). The exporter shows `mlx2_amoeba_rolling_layer`, `_rolling_chunk`, `_rolling_chunks`,
  `_rolling_layer_load_seconds`, `_rolling_layer_compute_seconds`, `_rolling_layer_stall_seconds`,
  `_rolling_state_bytes`, `_rolling_prefetched_bytes`, and the counters `_rolling_prefetch_stall_seconds_total` and
  `_rolling_load_seconds_total`.
- **Generation** can't run layer-major. On-policy continuations come from the normal serving route first and are
  then captured as fixed text; the carve stages need the model resident for this anyway.

### 27B parity evidence (2026-11-16)

Checkpoint `Qwen3.8-27B-BF16-q8-mlx2@2dd8d304`, 64 texts, window 2, 2 chunks. GPU windows rpar2 and rpar3 ran on
`ae30ac2ab`, rpar4 on `09606fec5`, and rpar5 on `7f83bed8d`.

**Result (rpar5, `7f83bed8d`): exact.** Responses and mu are bitwise equal on all 64 layers, NLL is within 4.8e-7,
and each layer is read once per chunk (124 layer loads for 63 streamed layers × 2 chunks). Every gap found before
that came from batching. The remaining response differences in rpar4 came through mu, because every peak is
measured from mu. The per-layer evaluation cut contributes nothing.

- **Streaming is exact.** Under the layer-major schedule, streamed and resident weights give bitwise-equal
  responses on all 64 layers, and bitwise-equal NLL. Two text-major resident runs are also bitwise equal.
- **Batch composition (fixed in `09606fec5`).** Chunks used to interleave texts, so a text's batch neighbours and
  the batch size differed from the resident capture's, and the kernels' tiling changed the numbers. Before the fix:
  NLL max 0.0106, 2.8M of 71M response elements over tolerance, top-1% neuron-set Jaccard as low as 0.977. Chunks
  are now whole resident batches. After the fix: NLL max 4.8e-7, 1 element over tolerance, top-1% Jaccard 1.0 in
  every layer.
- **mu (fixed after rpar4).**
  - The resident capture computes mu in a separate pass over the fit texts, batched among themselves, because it
    needs mu before it can compute the peaks.
  - Rolling's inline mu came from the fit rows of its main batches. |dmu| / max|mu| per layer was at most 3.7e-3
    (mean 6.3e-4, correlation 0.99999989), and 153k of 1.1M entries failed the 1e-3 relative + 1e-5 rule.
  - Pierre chose the extra pass. Rolling now carries the fit texts a second time, in the resident capture's own
    fit-only batches, and runs them under each layer's weights as they are loaded: extra compute, no extra weight
    read.
  - Each chunk gets a contiguous run of the fit batches, so the per-batch float32 sums are added in the resident
    order, across chunks too. This is bitwise equal to the resident mu on CPU, with one or two chunks and either
    carry.
  - The fit pass stops after the last dense layer.
  - `--mu-pass inline` keeps the single pass.
  - The plan counts the state twice when the model has dense units.
  - A batch clipped by a family's row cap is logged and recorded in the receipt as `batch_matches_resident: false`.

## Receipts and resume

```
<out>/build.json            model identity, inspection, plan, config, inputs (sha256 of the probe corpus,
                            manifest, taxonomy, core corpora), options, mlx2 commit
<out>/receipts/<stage>.json status, times, attempts, input digest, outputs (sha256), summary, error
<out>/events.jsonl          every progress event
<out>/logs/<stage>.log      every child's output
```

- A stage is skipped on resume only when its receipt is `done` and its input digest still matches. The digest
  covers the config, the fingerprint, the inputs and the upstream stages' output digests.
- A mismatch refuses, and `--redo STAGE` reruns that stage and the ones after it from nothing. Each one's
  directory and receipt are archived under `<out>/.redo/` and `receipts/`, so the old evidence stays
  distinguishable.
- Inside a stage, sub-steps resume from their own outputs: a capture with `meta.json`, a generation's
  `gen.partial.jsonl`, carve runs with `--resume`, and box-batch verdicts.
- `--stop-at HH:MM` stops cleanly (exit 75), and `resume` continues from there. No child starts after the deadline.
  A carve checkpoints and stops at it; any other sub-step that has already started (a capture, a generation, the
  gates) runs to its end.
- An interrupt (Ctrl-C, SIGTERM or SIGHUP) stops the child's process group (SIGKILL after 120 s) and marks the
  receipt `interrupted`.
- `resume` and the per-stage commands re-hash every input file and recheck the `--against` host's fingerprint.
  Any change refuses.
- Checkpoints are named `<artifact>@<fingerprint[:8]>`; a Hugging Face snapshot uses its repository name. Point
  the command at a directory or symlink named after the artifact, so that the carve's own receipts (which name the
  directory) agree.
- The fingerprint is checked again on every resume.
- A dirty tracked tree refuses unless `--allow-dirty` is given, because receipts name the commit.

## GPU windows

The model stages (`map`, `core`, `boxes`, `gates`) refuse to run on the GPU unless this process descends from
the owner of `/Users/Shared/mlxuag/gpu.lock`. Run them inside `scripts/run_with_gpu_locks.py`, adding
`scripts/run_with_service_paused.py` when :8282 must pause. Alternatively, `--gpu-window-owner LABEL` names the current
lock owner's label, when another job opened the window for this run; a label that doesn't match the lock refuses. `--cpu` runs every stage on the CPU. Generation defaults to an
mlx2 dev server on the model's best route on the GPU (`--gen-backend server`, port 8395). On the CPU it uses the
local ordinary-reference decode (`--gen-backend local`), and the receipt names the route used.

**Queueing behind other windows.** Queue through `scripts/amoeba27b_window_q.sh` (the queue gate, the :8282 pause,
the CPG lease and the GPU locks). Write your own `~/amoeba-runs/gate-27b-<tag>.pid` the moment you queue, and keep
that pid alive until your window ends. To run after another window, wait for its gate file with `AFTER_PID_FILE`.

The lowest-priority background map filler (`gate-27b-filler.pid`, Pierre 2026-11-16) uses the GPU whenever nothing
else is waiting. It yields within about 2–3 min to any other live `gate-27b-*.pid`. Never wait on the filler's gate:
treat it as absent. Write your own gate as usual; the filler sees it and yields.

## Targeted extraction (`extract`, workflow section 11.1)

```bash
mlx2 amoeba extract --model ~/mlx-models/<donor> --topic sci.biology --against ~/mlx-models/<host> --out DIR
```

`--topic` is a node id of `docs/research/amoeba-topics/taxonomy.v1.json`, for example `sci.biology`, `sci.medicine`,
`sci.physics`, `prog.c`, `prog.python` or `lang.fra`. An unknown id refuses before anything loads, and suggests
near matches.

Models below 8B are smoke tests only (Pierre, 2026-11-16 audit). A run on them, such as the Qwen3-0.6B build and
the Qwen3-1.7B-4bit extract, checks the pipeline. It is never a box-quality, map or transfer result.

| Stage | What it does |
|---|---|
| `gap` | The donor-gap screen. The topic's held probes (every held text at or below it) and a fixed per-topic sample of the rest (for the offset) are scored as per-byte NLL, bare and after a neutral prefix, on the donor and on `--against`. Both models score the same first 512 characters of each text, whatever their tokenizers. Gaps are centred on each condition's whole-corpus gap, computed without the topic; that offset's own bootstrap enters the interval. Extraction continues only when the donor leads in both conditions at 95%. The host is screened under its own memory plan, and `gap.json` records whether the tokenizers match. `--skip-gap-screen REASON` and `--force-extract REASON` are recorded in the bundle. |
| `core`, `map` | The donor's core and map, reused from a fingerprint-keyed cache (`research-artifacts/amoeba/cache/<fp>/`). The core's key is its settings, inputs and device. The map's key is its settings and the sha256 of the core it was clustered around, so a map is never paired with another core. A `build` publishes its core and map there too, except from a dirty tree. `--redo core` or `--redo map` carves afresh and replaces the cache entry, keeping the old one aside. The bundle names where its core and map came from (build, commit, device). |
| `box` | One box: the probes at or below the topic, plus continuations, with the core fixed. The cut is chosen on val at +0.03 and held is checked once at +0.05 (pooled). The mask is seeded from the map clusters whose **fit-split** tags reach the topic (+3 on their units, +1 elsewhere, `--init-raw`); held-confirmed labels never choose. A miss is listed in `next-round.json`. A covered box (its carve kept no units beyond the core) ends cleanly with a manifest that says so. |
| `box_gate` | Its detector, trained against English and off-topic probes (fit only), with held false-open and miss rates. |
| `box_bundle` | `manifest.json` (schema `mlx2.amoeba-box-bundle.v1`), the box mask, the packed box weights (`child_pack`: the box's gate/up rows and down columns, dequantized to float16), the gate, the core, the donor's map and taxonomy, the prompt set, the donor's measured quality and the gap result. |

`--attention-units heads` refuses: the carve host has no attention-head sites yet. The side-stream loader in
`mlx2 serve` is the next phase.

**A given core, no map, reserved texts (2026-11-18).** These options let a large dense donor get a box without
re-carving its core or capturing a full map:

- `--core-from NPZ[:KEY] --core-from-reason TEXT`: the `core` stage takes this mask instead of carving one. The
  mask must be a dense model's `[layers, intermediate]` core, for example the 27B T2 cut. It is never cached. Its
  sha256 and the receipts beside it are recorded in `core/core_source.json`, and the English-only check still
  runs on it.
- `--no-map REASON`: the map stage records the reason and nothing else. The box carve starts unseeded, and the
  bundle carries no map.
- `--exclude-texts FILE` (repeatable): a JSON object with any of `probe_ids`, `sha256` (of the text) and `groups`.
  Matching rows leave the build's effective probe corpus, `<out>/inputs/<probe build>/corpus.jsonl`, which every
  stage reads: the box set, the gate negatives, the English check and the prompt set. A list that matches nothing
  refuses. The accounting is in `inputs/effective-probes.json`.
  - `scripts/amoeba_bridge_heldout.py` writes such a list for the held texts a bridge-lab topic run never touched.
    It replays the run's seeded selection on the CPU and checks the counts against a recorded review.
- `--extra-topic-corpus FILE` (repeatable): more probe-format rows (`id`, `topics`, `split`, `text`, `group`,
  `license`). Duplicate and excluded texts are dropped. A row whose group already sits in the other split refuses.
- `--swap-growth-gb N --swap-waiver TEXT` (every run command): the stage fails, and its child's process group
  is stopped, if system swap grows more than N GB over the run's start, checked before each child and on every
  footprint sample.
- `box/bar.json` (also in the box receipt and the bundle manifest) states pass or fail on each bar condition, with
  `<artifact>@<fingerprint>` and the mlx2 commit:
  - core + box held dCE within +0.05 nats of the full donor;
  - at most 0.5x the held dCE of a same-count random box, with a margin floor.

The 27B sci.physics window, `scripts/amoeba27b_physbox_inner.sh OUT`, uses all of these.

## Installing a box in another model (`install`, workflow sections 12.2–12.3)

```bash
mlx2 amoeba install --box <extract out>/box_bundle --donor ~/mlx-models/<donor> --host ~/mlx-models/<host> --out DIR
```

`--routes` picks any of `side,tile,lora,bridge` (default: `side`, as workflow section 12.3; the others are experimental options). `--teacher box` (default) makes the bundle's core
plus box the teacher: the extracted expert. `--teacher full` uses the whole donor. `--set KEY=VALUE` changes a
route setting, for example `epochs=2`, `data.n_test=200` or `lr.bridge=5e-4`. `--profile quick` is a pipeline
check, never a transfer claim. Runs where either model is below 8B are labelled smoke tests in every receipt
and in the bundle.

| Stage | What it does |
|---|---|
| `pair` | Checks the bundle against `--donor`: the fingerprint must match the manifest. Requires the two tokenizers to be byte-identical, because every route pairs tokens by id; a string-id map for the side stream is not built. Records the joint memory plan, which sums both models' weights against the per-process cap and refuses when they don't fit together. |
| `topo` | Picks the donor's box layers: the interior layers with the most box units, at least two apart. Warps them to the host by relative depth; a CKA-fitted warp is not built. |
| `route_side` | The bundle's core plus box run beside the host, blended at the output through the bundle's gate detector. A window opens when the running mean of the token probability reaches the gate's threshold. Controls: the host alone, the core plus a same-count random set of units, the gate always open, and the whole donor. Reports the gate's open rate on held topic texts and on English (false opens). |
| `route_tile` | Gated tiles in the host, trained by full-vocabulary KL to the teacher on the topic's fit probes. Controls: the untrained tiles, which equal the host, and tiles trained on the core plus random units, at the same capacity. |
| `route_lora` | The same, with a gated low-rank linear adapter: the audit's gated-LoRA arm. |
| `route_bridge` | A learned low-rank gated map from the box units' activations to host writes. Its starting point is a ridge fitted on the topic's training text onto −dKL/dh; that is a training initialisation, not the broad-data ridge maps of section 12.2 item 3, which are not built. Controls, each at the same feature width: random donor units, the host's own topic units read from a clean host copy (no donor), another text's box features, and noise. |
| `report` | For each route, compares the main arm with each control by a paired bootstrap over held texts. The verdict is `transfers` (it beats the host and every control, within the drift cap), `helps, not specific` (it beats the host only), `drifts`, or `no gain`. Writes the install bundle (`report/`, schema `mlx2.amoeba-install.v1`): verdicts, route results, trained parameters, and the pair and topo files. |

Rules that apply to every route:

- **Text the routes use.** They train on the topic's fit-split probe texts, cut to 64 tokens. Validation comes
  from whole source groups. Held-split texts only score, and never choose an epoch, a unit or a threshold.
- **Scored span.** Every text is scored from its third token, in nats per byte, as the donor-gap screen scores
  it. The tokenizer's BOS token is prepended when it has one.
- **Write cap.** Every write and tile is capped per token at `norm_budget` (0.25) times the host layer's own
  increment. The host's residual is carried in float32 from layer 0, in every host pass, so a capped write is
  not rounded away.
- **Drift cap.** Every trained arm's English drift weight grows fourfold after each epoch over the 0.05 drift
  cap, so no arm buys its score with drift a control is denied.
- **One process.** The routes run donor and host in one process: they need the donor in lockstep, or as the
  teacher. This is declared in the plan (`processes`).

**Not built:**

- MoE expert units in the box (the routes read dense MLP units).
- The CKA warp.
- A host stub taken from the host's own map (it is chosen contrastively inside the bridge route).
- Donor continuations as training text (the routes train on probe text only).
- Generation-scored tasks.

The evidence so far is a smoke test (Qwen3-4B → 0.6B, `docs/research/amoeba-bridge-lab/`). With a filter that keeps
only the donor's correct traces, the bridge closed 63% of an arithmetic gap, and the distilled tile and gated-LoRA
arms about half. The bridge carried donor information: fed the host's own features at the same size, it gained 7
points (CI includes 0), against 32 from the box. No box-versus-random specificity was shown.
